# 이지스피크(EZspeak) 지역 SEO 페이지 스펙
`{지역} 영어회화` 키워드 상위노출을 위한 생성기 재작성 스펙 (네이버 + 구글 동시 최적화)

- 대상 파일: `generate_pages.py` (재작성), `data/regions.json`(7,334개 입력), `data/seo_pools.json`(콘텐츠 풀, 본 스펙과 세트)
- 이 문서는 **구현 스펙**이다. 재작성 에이전트는 이 문서와 `data/seo_pools.json`을 그대로 구현하면 된다.
- 현재 코드 기준선(재작성 전): `render_region_page()`가 intro/feature/cta/meta 4종 각 6개 변형(해시 선택)으로 지역 페이지를 생성하고, `render_hub_page()`가 전체 7,334개 링크를 시·도별로 그룹핑해 1개 허브 페이지에 나열, `LocalBusiness` JSON-LD(주소 없음, areaServed만 있음), `sitemap.xml`(flat, url만 나열)을 만든다.

## 0. 핵심 결정 요약

| 항목 | 결정 |
|---|---|
| URL/파일명 | **유지** — `지역/{keyword}-영어회화.html` |
| 내부 링크 구조 | 허브(전국) → 시·도(17) → 시·군·구 → 동·읍·면·축약, **4단계 계층**으로 전환 (현재는 허브 1페이지에 7,334개 링크 flat 노출 → 계층화) |
| 구조화 데이터 | `@graph`로 LocalBusiness/EducationalOrganization(공통 1개 실체) + FAQPage + BreadcrumbList 결합. **지역마다 별도 사업체가 있는 것처럼 표현하지 않음** (도어웨이 회피 핵심) |
| 콘텐츠 다양성 | title 5종 × faq 14세트(페이지당 4~5 선택) × local_intro 유형별 4종 × body_block 10종(페이지당 2~3 선택) × meta 5종 → 조합 수가 7,334보다 압도적으로 많아 중복 위험 사실상 없음 |
| 본문 최소 분량 | 내비/푸터 제외 가시 텍스트 기준 **1,200자 이상**(공백 포함) |
| 네이버 | 서치어드바이저 등록·소유확인·사이트맵 제출은 **사용자 액션** (자동화 불가). 마크업은 심플한 정적 HTML + 명확한 h1~h3 구조 유지로 대응 |

## 1. 현재 상태 요약 (재작성 전 기준선)

`generate_pages.py` (677줄) 구조:

- `kw_hash(keyword, salt)` / `pick(variants, keyword, salt)`: 키워드+salt 기반 MD5 해시로 변형 리스트에서 결정적 선택. salt별로 `intro`, `feature`, `cta`, `meta` 4종 콘텐츠 함수가 있고 각각 **6개 변형**을 가짐 (이번 재작성에서 확장).
- `full_location(kw)`: parents를 `·`로 join + keyword → 전체 지명 문자열. **문제점**: `type=="축약"`인 키워드 중 parents가 서로 무관한 여러 지역(예: `부산` → `경기도 오산시`, `부산광역시`, `전남광주통합특별시 장흥군`)을 동시에 갖는 경우가 있어, 그대로 합치면 "경기도 오산시·부산광역시·전남광주통합특별시 장흥군 부산"처럼 의미가 통하지 않는 문장이 만들어짐. → 3절 "축약형 처리 규칙"에서 수정.
- `render_region_page()`: hero(H1+intro) → features(3단계 프로세스, feature_lead H2) → CTA → nearby(인근 지역, 최대 10개) → footer. LocalBusiness JSON-LD 1개(주소 없음).
- `render_hub_page()`: 시·도별 `<details>`로 그룹핑하되 **7,334개 링크를 전부 최초 HTML에 렌더링**하고 클라이언트 검색(JS)으로 필터링. 크롤러 입장에서는 허브 1페이지에서 depth-1로 7,334개 페이지에 모두 도달 가능한 flat 구조.
- `render_sitemap()`: 메인+허브+지역 7,334개 URL을 단일 sitemap.xml에 flat 나열.
- `regions.json` 스키마: `{"keyword", "type": "동|구|군|시|읍|면|축약", "parents": [...]}`. 실측 분포: 축약 3,142 / 동 2,713 / 면 1,016 / 읍 220 / 시 85 / 군 81 / 구 77.
- 데이터 이슈 발견: `parents`에 `전남광주통합특별시`처럼 실제 존재 여부가 불확실한 행정구역명이 포함된 항목이 있음 → 8절 QA 체크리스트에 기재.

## 2. Title / Meta 패턴

### Title (해시 로테이션, `data/seo_pools.json` → `titles`)

플레이스홀더는 `{keyword}`만 사용(짧고 안정적인 길이 유지, parents 깊이와 무관). 5종:

```
{keyword} 영어회화 학원 | 이지스피크
{keyword} 영어회화 | 1:1 원어민 회화 이지스피크
{keyword} 영어회화 학원 추천 | 이지스피크
{keyword} 영어회화 원어민 수업 | 이지스피크
{keyword} 영어회화 무료 레벨테스트 | 이지스피크
```

- 원칙: 키워드를 **title 맨 앞**에 배치(네이버·구글 모두 앞쪽 토큰 가중치가 높음), 브랜드명은 뒤에 `|`로 구분.
- 길이: 실측 19~27자(대부분 지역 키워드 2~5자 기준) — 구글 SERP 절단 기준(약 60byte/32~35자 한글) 안전권.
- 선택 규칙: `pick(pools["titles"], keyword, "title")`.
- 허브 페이지, 시·도/시·군·구 페이지는 별도 고정 title 사용(5절 참고), 이 풀은 최말단 동/읍/면/축약 페이지 전용.

### Meta description (`seo_pools.json` → `meta_descriptions`, 5종)

- 플레이스홀더: `{keyword}`, `{loc}`.
- 길이: 실측 79~91자(신림동/정자동 등 다양한 depth로 검증) → 목표 범위 80~110자에서 크게 벗어나지 않음. 사용 시 110자를 넘기지 않도록 재작성 에이전트가 `len()` 체크 후 초과분은 뒤 문장부터 잘라내는 안전장치를 넣을 것.
- 원칙: 키워드 포함 + 핵심 제공가치(1:1 원어민, 무료 레벨테스트, 학습 관리) 1개 이상 + CTA성 어미(~보세요/~있습니다)로 클릭 유도. 과장 표현("업계 1위", "100% 보장" 등) 금지 — 표시광고법 및 스팸 정책 리스크.
- 네이버는 자체 스마트블록 요약 로직으로 description을 그대로 쓰지 않는 경우가 많으므로, **본문 첫 문단(intro)** 도 요약문 역할을 하도록 핵심 정보를 앞에 배치해야 한다(6절 참고).

## 3. URL / 파일명

**결정: 유지한다.** `지역/{keyword}-영어회화.html`

근거:
1. 이미 7,334개 파일이 존재하고 `sitemap.xml`에 등재되어 있어, URL을 바꾸면 색인 초기화 + 301 리다이렉트 맵 관리 부담이 발생한다. 아직 실배포/색인 전이라도, 재작성 때마다 URL을 흔들 이유가 없다.
2. 파일명 자체에 키워드(`{keyword}`)와 검색 의도(`-영어회화`)가 그대로 노출되어 URL 자체가 이미 키워드 매칭에 유리하다 (구글/네이버 모두 URL 슬러그의 키워드 포함을 긍정 신호로 본다).
3. 계층 구조(4절)는 **URL 경로 깊이가 아니라 내부 링크 그래프**로 구현할 수 있으므로 `/지역/` 단일 폴더를 유지해도 무방하다. 실제로 시·도(`서울특별시-영어회화.html`)·시·군·구(`관악구-영어회화.html`)·동(`신림동-영어회화.html`) 페이지가 이미 모두 `regions.json`에 **개별 keyword로 존재**하므로, 별도의 새 페이지 타입을 만들 필요 없이 이 기존 페이지들을 계층의 중간 노드로 재활용하면 된다.
4. 향후 실제 도메인 확정 후 URL 체계를 바꿔야 한다면, 그 시점에 반드시 301 리다이렉트 맵을 별도 산출물로 관리할 것(8절 체크리스트).

## 4. 내부 링크 계층 (크롤링 효율화)

### 4.1 문제

현재 허브(`지역/index.html`) 1페이지가 7,334개 링크를 전부 초기 HTML에 렌더링한다. 구글이 이를 처리하지 못하는 것은 아니지만, "실제 탐색 가능한 계층 없이 검색엔진 접근을 위해서만 존재하는 대량의 유사 페이지 목록"은 구글 스팸 정책의 도어웨이 판정 요소(“a clearly defined, browseable hierarchy”의 부재)와 정확히 겹친다. 또한 허브 1페이지에서 PageRank가 7,334개로 즉시 분산되어 개별 지역 키워드의 랭킹 신호가 희석된다.

### 4.2 해결: 4단계 계층 (기존 데이터로 구현 가능, 새 페이지 타입 불필요)

```
지역 허브 (지역/index.html)
  └── 시·도 페이지 17개  (regions.json 의 type="시" 항목, 예: 서울특별시-영어회화.html)
        └── 시·군·구 페이지 (type="구"/"군", 예: 관악구-영어회화.html)
              └── 동·읍·면 페이지 (type="동"/"읍"/"면", 예: 신림동-영어회화.html)
        (축약형은 대표 parent 체인에 종속 링크로만 연결, 3.1 참고)
```

- `regions.json`의 `parents` 배열 길이로 depth를 판별한다: `parents=[]` → 시/도(최상위), `parents=[시도]` → 구/군/시(2단계), `parents=[시도, 구/시]` → 동/읍/면(3단계, 예: 분당구 산하 정자동). 구현 시 각 페이지의 자식 목록은 "내 keyword가 상대방 parents 배열의 마지막 원소와 문자열 일치"로 계산.

### 4.3 페이지별 상향/하향/측면 링크 규칙

| 페이지 유형 | 상향(위) | 하향(아래) | 측면(옆) |
|---|---|---|---|
| 지역 허브 | 메인 홈(`../index.html`) | 시·도 17개 전체 (가시 HTML에 전부 노출 — 17개는 도어웨이 리스크 없음) | — |
| 시·도 (예: 서울특별시) | 지역 허브 | 관할 구·군·시 전체 (통상 10~30개, 전부 노출 가능) | 다른 시·도로의 직접 링크 없음(허브 경유) |
| 시·군·구 (예: 관악구) | 상위 시·도 + 허브(브레드크럼) | 관할 동·읍·면 전체. **20개 초과 시** 가나다순 anchor 그룹 또는 상위 12개 노출+"전체 보기"로 페이지 내 나머지 표시(전부 HTML에는 존재하되 시각적으로 접힘) | 같은 시·도 내 인접 구·군 6~10개 (기존 sibling 로직을 이 depth에도 적용) |
| 동·읍·면 (예: 신림동) | 상위 구·군·시 + 상위 시·도(브레드크럼 전체 경로) | 없음(최하위 노드) | 같은 부모(구/군/시) 공유하는 인근 동·읍·면 최대 10개(기존 로직 유지) + 대응 축약형 상호링크(예: 신림동 ↔ 신림) |
| 축약형 (예: 신림, 서면, 부산) | **대표 parent 1개만 선택**(3.1 참고)의 체인 | — | 동일 대표 지역을 공유하는 다른 축약형(있다면) |

- 모든 페이지에 **브레드크럼**(시각적 HTML + `BreadcrumbList` JSON-LD, 5.3절)을 넣어 상향 경로를 명시한다: `홈 › 전국 지역별 영어회화 › {시·도} › {시·군·구} › {keyword}`.
- 허브 페이지의 클라이언트 검색(JS 필터)은 UX 목적으로 계속 유지하되, **1차 크롤 대상은 시·도 17개로 한정**한다. 동 단위 페이지는 sitemap.xml(전체 등재 유지) + 시·군·구 페이지의 하향 링크 + 인근 동 측면 링크, 이렇게 최소 2개 경로로 발견 가능해야 한다(허브 직링크 없이도 3~4 클릭 이내 도달).

### 4.4 축약형(type="축약") 처리 규칙

`regions.json`에는 하나의 축약 키워드가 서로 지리적으로 무관한 여러 `parents`를 가진 경우가 있다(예: `부산` → 경기도 오산시 / 부산광역시 / 전남광주통합특별시 장흥군). 이를 그대로 이어붙이면 문장이 깨지고, "한 페이지가 서로 무관한 여러 지역을 동시에 서비스한다"는 인상은 도어웨이 신호로도 읽힐 수 있다.

**규칙**:
1. 대표 parent 선정: parents 중 (a) 키워드와 발음/표기가 가장 직접적으로 대응하는 광역 행정명(`~광역시`/`~특별시`/`~도`)이 있으면 그것을 대표로 선택, (b) 없으면 parents 배열의 첫 번째 항목을 대표로 선택.
2. `loc`(본문 노출용 전체 지명)은 **대표 parent 1개 + keyword**로만 구성한다. 나머지 parents는 화면 본문에 나열하지 않는다.
3. 나머지 parents는 상향/측면 링크 계산(4.3) 용도로만 내부적으로 사용 가능하되, 이 역시 대표 parent 체인을 우선한다.
4. `local_intros.축약` 문구(`seo_pools.json`)는 이미 이 원칙에 맞춰 "정확한 행정구역명과 무관하게 상담으로 안내"하는 톤으로 작성되어 있으므로 그대로 사용.

## 5. 페이지 구조 (H1~H3), 콘텐츠 섹션, 구조화 데이터

### 5.1 아웃라인

```
H1: {keyword} 영어회화                              ← 유일, 키워드 그대로, 페이지당 1개
  [브레드크럼 HTML: 홈 › 전국 지역별 영어회화 › {시도} › {구군} › {keyword}]

  [Hero / 인트로 섹션]
  - 가시 텍스트: local_intros[type] 1개 + 기존 intro_paragraph 1개 (두 문단)
  - SEO 역할: 검색 스니펫/네이버 스마트블록 요약 소스, 지역 유형별 자연스러운 진입점

H2: {keyword}에서 영어회화, 이렇게 시작하세요        ← 지역 맞춤 문단 (local_intro + 부가 설명)
  - SEO 역할: 키워드 2차 배치, 지역성 신호 강화(사람이 쓴 지역 설명처럼 보이게)

H2: 이지스피크 {keyword} 커리큘럼 & 운영 방식          ← 커리큘럼/운영방식 (기존 process-timeline 유지)
  H3: 1:1 원어민 수업
  H3: 1:1 한국인 플래너 밀착 케어
  H3: 다양한 부가 컨텐츠
  + body_blocks 중 2~3개 추가 삽입(수강대상/커리큘럼구성/레벨테스트/학습관리 등 실질 정보)
  - SEO 역할: 본문 분량 확보 + 실질적 정보로 "도어웨이 아님"을 증명하는 핵심 섹션

H2: {keyword} 영어회화 자주 묻는 질문                  ← FAQ 4~5개 (해시 선택)
  H3: (각 FAQ 질문 텍스트 그대로, FAQPage schema question과 100% 동일 문구)
  - SEO 역할: 구글 FAQ 리치리절트 후보, 롱테일 질의 매칭, 체류시간 증가

H2: {sibling_key} 인근 지역 영어회화                   ← 기존 nearby 섹션 유지 (최대 10개)
  - SEO 역할: 내부 링크 그래프 (4절), 페이지별 고유 콘텐츠(목록 자체가 지역마다 다름)

[CTA 섹션] 무료 레벨테스트 신청 버튼 (기존 유지)
```

### 5.2 키워드 배치 / 밀도 가이드

- H1에 정확히 1회, 첫 문단(인트로) 첫 문장 안에 1회, 이후 본문 전체에 자연스럽게 4~8회 분산(정확 일치 `{keyword} 영어회화` + 변형 `{keyword}에서 영어회화`, `{keyword} 지역` 등).
- 목표 밀도: 가시 텍스트 총량 대비 **1.5~2.5%** (예: 1,400자 본문이면 정확/변형 키워드 언급 21~35회 내외가 아니라, **어절 기준**으로 계산 — 국문 특성상 음절 밀도가 아닌 "키워드가 포함된 문장 수 / 전체 문장 수"로 대략 15~25% 문장에 키워드가 자연스럽게 등장하는 정도가 실무적으로 안전). 절대 문장마다 키워드를 반복하지 말 것(스팸 신호).
- 동의어/변형 사용 권장: "영어회화" ↔ "회화 수업" ↔ "스피킹" ↔ "말하기 연습" 등을 섞어 키워드 스터핑처럼 보이지 않게 한다.

### 5.3 구조화 데이터 (그대로 붙여넣는 완성 템플릿)

**설계 원칙 (도어웨이 회피의 핵심)**: LocalBusiness를 지역마다 별개 사업체처럼 생성하지 않는다. 실제 사업 실체는 하나이며(온라인 1:1 화상 수업 + 필요 시 상담), `@id`를 전 페이지 공통으로 고정해 "동일 실체가 이 지역도 서비스한다(`areaServed`)"는 의미로만 사용한다. 이는 구글이 명시한 도어웨이 예시("여러 페이지가 특정 지역을 타겟팅하지만 실제로는 한 곳으로 유도")를 피하는 방법이자, 실제 사실과도 부합한다(허위 다지점 암시 금지).

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@graph": [
    {
      "@type": "EducationalOrganization",
      "@id": "{{BASE_URL}}/#business",
      "name": "{{BUSINESS_NAME}}",

      },
      "knowsLanguage": ["ko", "en"]
    },
    {
      "@type": "WebPage",
      "@id": "{{CANONICAL_URL}}#webpage",
      "url": "{{CANONICAL_URL}}",
      "name": "{{TITLE}}",
      "description": "{{META_DESCRIPTION}}",
      "about": { "@id": "{{BASE_URL}}/#business" },
      "isPartOf": { "@id": "{{BASE_URL}}/#website" }
    },
    {
      "@type": "BreadcrumbList",
      "@id": "{{CANONICAL_URL}}#breadcrumb",
      "itemListElement": [
        { "@type": "ListItem", "position": 1, "name": "홈", "item": "{{BASE_URL}}/" },
        { "@type": "ListItem", "position": 2, "name": "전국 지역별 영어회화", "item": "{{BASE_URL}}/지역/index.html" },
        { "@type": "ListItem", "position": 3, "name": "{{SIDO}}", "item": "{{SIDO_URL}}" },
        { "@type": "ListItem", "position": 4, "name": "{{PARENT}}", "item": "{{PARENT_URL}}" },
        { "@type": "ListItem", "position": 5, "name": "{{KEYWORD}}", "item": "{{CANONICAL_URL}}" }
      ]
    },
    {
      "@type": "FAQPage",
      "@id": "{{CANONICAL_URL}}#faq",
      "mainEntity": [
        {
          "@type": "Question",
          "name": "{{FAQ_Q_1}}",
          "acceptedAnswer": { "@type": "Answer", "text": "{{FAQ_A_1}}" }
        },
        {
          "@type": "Question",
          "name": "{{FAQ_Q_2}}",
          "acceptedAnswer": { "@type": "Answer", "text": "{{FAQ_A_2}}" }
        },
        {
          "@type": "Question",
          "name": "{{FAQ_Q_3}}",
          "acceptedAnswer": { "@type": "Answer", "text": "{{FAQ_A_3}}" }
        },
        {
          "@type": "Question",
          "name": "{{FAQ_Q_4}}",
          "acceptedAnswer": { "@type": "Answer", "text": "{{FAQ_A_4}}" }
        }

    }

```

구현 메모:
- `BreadcrumbList`의 3~4번째 항목(`{{SIDO}}`, `{{PARENT}}`)은 depth에 따라 가변(시·도 페이지 자체라면 3번 항목에서 끝, 구/군 페이지라면 4번에서 끝, 축약형은 대표 parent 체인 기준). 재작성 시 배열 길이를 depth만큼 동적으로 생성할 것.
- `EducationalOrganization`의 `@id`는 **모든 페이지에서 동일한 문자열**(`{{BASE_URL}}/#business`)을 사용해 하나의 실체로 통합한다. 페이지마다 다른 주소/전화번호를 넣지 않는다. 실제 오프라인 지점이 있는 경우에만 `LocalBusiness` + `address`(PostalAddress)를 추가하되, 이때도 지점 수만큼만 정직하게 등록한다(9절 체크리스트 참고).
- `FAQPage`의 `Question.name`은 화면에 보이는 H3 텍스트와 **완전히 동일한 문구**여야 한다(구글 가이드라인 — 화면에 없는 내용으로 FAQ 스니펫을 노리는 것은 스팸 정책 위반).
- `image`, `telephone`, `email`은 기존 코드의 `BUSINESS_PHONE`/`BUSINESS_EMAIL` 상수를 그대로 사용.

## 6. 콘텐츠 섹션 구성 상세

1. **인트로**: 기존 `intro_paragraph()`(6종, 유지) + `seo_pools.json`의 `local_intros[type]`(유형별 4종) 중 하나를 이어붙여 2문단 구성. 유형별 톤을 다르게 하여(동=생활권, 구=광역 생활권, 군=원거리 대안, 시=도시 전역, 읍=중심 시가지, 면=농촌·화상수업 강조, 축약=모호성 안내) 자연스러움 확보.
2. **지역 맞춤 문단(H2)**: local_intro를 별도 H2 섹션으로 한 번 더 강조하거나, 인트로와 합쳐도 무방. 단 H2 타이틀에는 반드시 `{keyword}` 포함.
3. **커리큘럼·운영방식**: 기존 3-step(process-timeline) 유지 + `body_blocks`에서 2~3개 해시 선택하여 각 소제목(`title`)을 H3 또는 강조 문단으로 추가. 실질적 운영 정보(대상/시간표/교재/관리방식)를 담아 "검색엔진 없이도 유용한 페이지"라는 실질을 만든다.
4. **FAQ**: `seo_pools.json`의 `faq`(14세트)에서 `pick`으로 4~5개를 salt를 달리해(`faq0`~`faq4`) 중복 없이 선택. 질문은 H3, 답변은 본문 + FAQPage schema에 동일 문구로 반영.
5. **인근 지역 링크**: 기존 로직 유지, 4절의 계층 규칙에 맞춰 depth별 sibling 정의를 확장.
6. **CTA**: 기존 `cta_copy()`(6종) 유지.

## 7. 네이버 특화 대응

네이버는 구글과 색인/랭킹 로직이 달라 별도 대응이 필요하다.

- **서치어드바이저 등록·소유확인·사이트맵 제출은 자동화 불가 — 사용자 액션** (8절 체크리스트 1~3번).
- **선호 마크업/구조**: 과도한 JS 렌더링 의존 없는 심플한 정적 HTML(현재 방식 그대로 적합), 명확한 `h1 → h2 → h3` 계층, `<title>`/`<meta name="description">` 필수, 이미지 `alt` 속성 채우기(현재 logo `alt`는 있으나 본문 내 아이콘 SVG는 `aria-hidden` 처리 유지), 모바일 반응형 유지(기존 `style.css` 대응 확인).
- **첫 문단 요약 최적화**: 네이버는 검색 결과에 자체 스마트블록/AI 요약을 노출하는 경우가 많아 `<meta description>`이 그대로 노출되지 않을 수 있다. 따라서 **본문 첫 문단(인트로)** 자체가 이미 핵심 정보(지역명+제공가치+CTA 암시)를 담도록 작성한다 — 이번 스펙의 `local_intros`+`intro_paragraph` 결합 구조가 이를 충족.
- **색인 롤아웃 전략**: 신규 도메인은 네이버 신뢰도가 낮게 시작하므로, 7,334개를 한 번에 "웹페이지 수집요청"하지 말고 사이트맵은 전체 제출하되, 수집요청(일일 제한 있음)은 검색량이 많은 대표 키워드(구 단위, 대형 상권 동)부터 우선순위를 두고 순차 진행. 최소 2~4주 간격으로 노출 여부를 모니터링.
- **섹션 분리 노출 한계**: 네이버는 웹문서/블로그/카페/지도가 분리 노출되므로 웹문서만으로는 노출 지분에 상한이 있을 수 있다. 지도(스마트플레이스), 블로그 등 타 섹션 보완은 이 스펙의 범위 밖이지만 8절 체크리스트에 옵션으로 기재.

## 8. 도어웨이 판정 회피 (구글 스팸 정책 대응)

구글 스팸 정책은 "여러 페이지가 특정 지역/도시를 타겟팅하지만 실제로는 한 곳으로 유도", "검색엔진이 없으면 존재 이유가 없는 페이지", "탐색 가능한 계층 없이 검색 노출만을 위해 생성된 대량의 유사 페이지"를 도어웨이로 정의한다. 대응책:

1. **콘텐츠 조합 다양화(정량적 근거)**: title 5 × faq C(14,5)=2,002가지 조합 × local_intro 유형별 4 × body_block C(10,3)=120가지 조합 × meta 5 × 기존 intro/feature/cta 각 6 → 조합 공간이 7,334보다 수 자릿수 크다. 동일 salt 체계를 유지하면 페이지마다 사실상 유일한 조합이 나온다.
2. **페이지 고유의 실제 값**: H1/키워드, 인근 지역 링크 목록(자체가 지역마다 다름), 브레드크럼 경로가 전부 지역마다 유일 — 콘텐츠 풀 조합과 무관하게 이미 페이지별 고유성이 있음.
3. **다지점 허위 암시 금지**: 5.3절 원칙대로 LocalBusiness/EducationalOrganization을 페이지마다 별개 실체로 만들지 않는다. 실제로 서비스하지 않는 지역에 물리적 지점이 있는 것처럼 암시하지 않는다.
4. **실질적 자기완결성**: 각 페이지가 FAQ, 운영방식, CTA를 통해 "그 자체로 방문할 가치가 있는 랜딩페이지" 역할을 하도록 body_blocks/FAQ를 충분히 채운다(5.4절 분량 기준 충족).
5. **확장 여지(스트레치 목표, 지금 당장 데이터 없음)**: `regions.json`에 지역별 실제 정보(인근 지하철역, 대표 상권명, 학군 특징 등) 필드를 추가하면 body_blocks를 사실 기반으로 더 세분화할 수 있다. 현재는 해당 데이터가 없으므로 콘텐츠 풀 조합 방식으로 대체하되, 향후 데이터가 확보되면 우선 반영 권장.
6. **생성 후 자동 QA 권장**: 재작성된 생성기에 아래 체크를 추가할 것 — (a) 페이지별 가시 텍스트 길이 ≥1,200자 검증, (b) 동일 (intro, feature, cta, meta, faq-set, body_block-set) 조합이 2개 이상 페이지에서 발생하는지 카운트, (c) FAQ의 Question.name과 화면 H3 텍스트 일치 여부 검증. 실패 시 빌드 실패 처리 권장.

## 10. `seo_pools.json` 사용 계약 (재작성 에이전트용 요약)

- 파일 위치: `data/seo_pools.json` (본 스펙과 동일 디렉터리).
- 최상위 키: `titles`(5), `meta_descriptions`(5), `faq`(14, `{q, a}`), `local_intros`(type별 4), `body_blocks`(10, `{title, text}`).
- 플레이스홀더: `{keyword}`, `{loc}`, `{parent}`, `{sido}` — 정의는 파일 내 `_meta.placeholders` 참고. Python `str.format(**ctx)`로 치환 가능하도록 작성되어 있음(중괄호 이스케이프 불필요, 텍스트 내 다른 중괄호 없음).
- 선택 규칙: 기존 `pick(variants, keyword, salt)` 함수를 그대로 재사용하되 salt를 콘텐츠 종류별로 구분(`title`, `meta`, `local_intro`, `faq0`~`faq4`, `body0`~`body2`). FAQ/본문 블록은 여러 개를 뽑아야 하므로 `salt`에 인덱스를 붙여 서로 다른 해시값을 얻는다(예: `faq0`, `faq1`, `faq2`, `faq3`으로 4개를 뽑되 중복 인덱스가 나오면 다음 salt로 재시도하거나 modulo 결과가 겹치지 않도록 이미 뽑은 인덱스는 제외 리스트에서 순차 선택).
- `local_intros`는 `kw["type"]` 값을 그대로 키로 사용(동/구/군/시/읍/면/축약). `type`이 빈 문자열이거나 알 수 없는 값이면 "동" 풀을 기본값으로 폴백.
